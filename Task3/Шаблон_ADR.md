#### Ключевые архитектурные решения

1. **Сервис ставок** — вынесен в отдельный микросервис с кэшированием для решения проблемы загрузки справочников. Обеспечивает быстрый отклик (<500 мс) для веб-интерфейса и кол-центров. Разработан на NET.Core - технологии знакомой сотрудникам it банка
2. **Сервис обработки заявок** — вынесен в отдельный микросервис, обрабатывает заявки и сохраняет в АБС. Разгружает АБС от онлайн-нагрузки.
3. **Интернет-банк** - помещен в кластер в основном и резервном ЦОД для **масштабирования нагрузки**, перед ними внедрен балансировщик нагрузки для **отказоустойчивости**.

### `<a name="_bjrr7veeh80c"></a>`**Альтернативы**

Опишите здесь наиболее важные альтернативные решения.

1. Прямой запрос ставок из АБС в веб-интерфейс: Не решает проблему загрузки >1с; создаёт высокую нагрузку на АБС.
2. Доступ кол-центра напрямую к АБС: Нарушает безопасность; требует сложной настройки прав; АБС не предназначена для высоконагруженных запросов.
3. Хранение ставок только в файле для внутренннего и партнёрского кол-центра: Нет актуальности в реальном времени; ручное обновление; нет API для внутреннего кол-центра

**Недостатки, ограничения, риски**

Подробно опишите здесь недостатки, ограничения и риски выбранного решения.

1. **Зависимость от АБС** - При недоступности АБС заявки не попадут в дальнейшую обработку. Риск частичной недоступности сервиса.
2. **Ограничение АБС** - Вертикальное масштабирование АБС создаёт «бутылочное горлышко» при росте нагрузки.
3. **Сложность развёртывания** - Увеличение числа компонентов требует настройки мониторинга, логирования, CI/CD
4. **Безопасность** - Передача файлов партнёрскому кол-центру требует шифрования и контроля целостности
